# OBS-08-E010：WAIT 保存与执行校验不一致

状态：修复完成、回归通过，等待模块结果审核。此处是一项观察的多个复现切面，不把工程失败次数算成新增 Bug 数量。

## 前置条件

使用全新隔离 QA 账号和项目，创建启用环境 `qa`。有权创建、编辑接口自动化场景及公共步骤；无实际 Runner 目标请求参与以下保存复现。迁移/同步使用两个自有隔离项目。

## 复现一：保存小数，执行端才失败

1. 向 `/api/v1/projects/{projectId}/api-automation/scenarios` 发送 POST，HTTP JSON 正文如下；`delayMillis` 是数字，不加引号。

```json
{
  "name": "D16-WAIT-REPRO",
  "description": "",
  "environmentCode": "qa",
  "failureStrategy": "STOP",
  "variables": {},
  "preRequestScript": "",
  "postResponseScript": "",
  "steps": [
    {
      "id": "request",
      "type": "REQUEST",
      "name": "请求",
      "config": {"method": "GET", "url": "https://8.8.8.8/qa"}
    },
    {
      "id": "wait",
      "type": "WAIT",
      "name": "等待",
      "config": {"delayMillis": 1.5}
    }
  ]
}
```

2. 读取场景详情与修订列表，检查是否已经持久化。
3. 在受控 Runner 夹具中对该定义进行执行预检，记录保存端与执行端的差异；不向示例 URL 发真实请求。
4. 对已有场景以当前版本 PUT 相同非法 WAIT，核对版本、修订及业务审计。

修复前：POST/PUT 可接受小数；校验使用 `longValue()` 丢掉小数部分，但原小数配置仍可保存，随后被 Runner 的整数约束拒绝。预期：在保存时返回 400，现有记录、版本、修订和成功业务审计均不改变。

修复后：新建、编辑、公共步骤、迁移/同步、新入队均采用同一精确整数判断。用例 `TC-D16API-04/12/14/16/18/20/21/23`。

## 复现二：微小小数先丢精度而被放行

1. 将正文中的 WAIT 改为原始数字 `1.0000000000000001`。
2. 使用原始 HTTP 字节提交，不先用 JavaScript `JSON.parse/JSON.stringify` 处理该数字。
3. 检查 HTTP 状态、保存值及新修订是否产生。
4. 在公共步骤、迁移及同步资料中的同一路径重复操作。

修复前：无类型 JSON 解码可能先变成 Double，精度丢失后校验无法知道原值有小数部分。预期：按原精度判定为非整数，400 且不写入。

修复后：局部步骤配置和同步定义读取保留 `config.delayMillis` 的精度，之后再检查整数和值域；未改应用全局 ObjectMapper。`TC-D16API-05/14/16/18` 和真实 JAR 原始 HTTP 验收通过。

## 复现三：溢出、数字字符串和非法类型

1. 先用 `18446744073709551616` 替换 WAIT 后提交。这是原始 JSON 数字。
2. 分别使用 `1e10000`、`"10"`、`" 10 "`、`true`、`[]`、`{}`、`null` 及缺失 `delayMillis`。
3. 另发送含裸 `NaN`、`Infinity`、`-Infinity` 的原始 JSON 正文。
4. 每次比较资产和修订数量，确认错误不产生部分业务写入。

修复前：大整数可能在 `longValue()` 时回绕后通过范围判断；数字字符串可通过旧 `Long.parseLong` 路径。数字字符串现按批准的 D16-N=A 收紧为拒绝，这属于明确的兼容变化。

修复后：有限、精确、范围内的 JSON number 才能通过；`10`、`10.0`、`1e1` 仍等价接受。非法原始 JSON、类型错误、非整数和溢出均受控拒绝。裸 NaN 的测试没有使用会将其变成 null 的序列化方法。`TC-D16API-01` 至 `10` 通过。

## 复现四：旧非法定义绕过新入队校验

1. 在旧版本产生含 WAIT=1.5 的定义，保留直接场景及被引用公共步骤/子场景的修订。在本次回归中，只在自有临时库模拟这些存量记录。
2. 在候选版本读取它们，确认仍可查看且没有批量改写。
3. 分别执行配置预览和新入队；再通过根场景引用旧公共步骤/子场景尝试入队。
4. 比较执行记录、已有清单及相关业务写入。
5. 人工明确将旧值改成合法整数 10 并保存，重新入队。

修复前：展开只检查结构与引用，非法 WAIT 可先进入执行队列。预期：读旧记录不做迁移，新入队前拒绝非法 WAIT；明确修复后可新入队，旧清单不变。

修复后：直接步骤及展开引用均重新验证；控制面的 Runner 租约生成继续保留原受限协议错误状态，不把坏配置送至目标执行。`TC-D16API-19/20/21/29/30` 通过。

## 复现五：页面先转换成 Number

1. 打开含 WAIT 的场景，选择等待步骤。
2. 输入 `1.5`，点击“保存场景”；再输入 `1.0000000000000001` 重复操作。
3. 检查输入是否被先舍入、是否发送保存请求。
4. 对照输入 `10.0`、`1e1` 后手动保存。

修复前：页面先转换为 Number，未按批准规则阻止保存，微小小数可能先舍入。预期：保留输入文本完成精确判断，错误定位到 `config.delayMillis`，不发业务保存；合法编辑发送 JSON number。

修复后：页面先解析十进制位与指数，检查有无小数部分、有限整数和值域，再转换为数值。真实后台 Chrome 及组件回归均通过 `TC-D16API-24/25`。
