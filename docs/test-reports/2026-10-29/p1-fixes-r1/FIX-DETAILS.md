# 6项P1逐项修复与复现说明

本批选择已获批准，修复/回归结论仍待用户审核。测试使用自有临时账号、项目、数据库和会话；下列复现只能在隔离QA环境执行。历史观察不是新增登记的6个Bug，D11尤其属于已确认的权限契约。

## D02 · OBS-03B-E002 · 跨类型同名参数

**历史复现步骤**

1. 用有项目写权限的账号进入项目环境、参数与密钥，选择同一环境。
2. 新建密钥`P1_TYPE_KEY`，记录其ID、类型及密文。
3. 在普通参数入口保存同名`P1_TYPE_KEY`，填写另一普通值。
4. 刷新普通参数和密钥列表，并检查原记录与写入审计。
5. 反向操作：已有普通参数时，在密钥入口保存同名Key；再并发提交两种类型的同名创建。

**修复前**：允许隐式转换，原类型被覆盖。修复前定向10条中3条失败。

**落实规则**：按数据库现有唯一键范围、在同一项目锁内判断并写入；跨类型409，不改变ID、密文、值，不生成成功写入审计。同类型更新仍有效；无新增大小写转换或存量恢复。

**回归**：P1-D02-01～10；覆盖双向冲突、同类型、项目/环境隔离、trim、并发、权限、BASE_URL和校验。自由环境代码仍沿用旧契约，未顺带执行D01或共享P2观察。

## D05 · OBS-03D-E006 · 安全事件后的旧Session

**历史复现步骤**

1. 准备管理员A和目标账号B；在两个独立浏览器使用B登录，保留两个Session Cookie。
2. A停用B，然后分别用两个旧Cookie请求`GET /api/v1/auth/me`。
3. 用新隔离B账号重复步骤1，分别执行删除、管理员重置密码，再请求me及项目受保护读取。
4. 写操作使用旧会话并附新鲜CSRF，确认不能创建业务记录。
5. 停用后在旧Cookie尚未请求前重新启用；另验证重置后重启再使用旧Cookie，以及新旧密码的新登录。

**修复前**：安全事件后旧me仍可200，旧密码新登录会拒绝；不能据此推断所有旧业务写入均成功。修复前定向10条中5条失败。

**落实规则**：持久`security_version`在停用状态变化、删除和重置密码时递增。受保护浏览器请求校验当前账号、版本及口令摘要，旧Session401；重新启用不能复活。自改密码后清当前界面身份并去登录页。普通资料修改、其他管理员会话不受影响。P0：改密不额外吊销PAT；停用/删除仍拒绝PAT。

**回归**：P1-D05-01～10、P1-U05-01～03；兼容检查读取旧序列化账号缺失版本字段为0；真实JAR HTTP场景验证两个会话、重置、重启及新密码。安全事件提交前已进入执行的请求不承诺回滚。

## D11 · OBS-07-S005 · PAT读取权限

**历史行为复现步骤**

1. 在合法项目写角色下，分别签发仅`project:read`、仅`project:write`、两者兼有及仅`run:execute`的PAT。
2. 各令牌分别请求`GET .../api-debug/grpc/descriptors`及`GET .../api-debug/history`。
3. 在history中添加含草稿的记录后重复，再移除当前项目成员权限或改用另一项目。
4. 撤销PAT后再请求；不能凭浏览器Cookie回退取得明文。

**观察事实**：read能读描述符但history403，write能读history但描述符403。用户已选A，以上是本轮保留的正确契约，不是待放宽的缺陷。

**落实规则**：补明确的权限矩阵和说明，保留原history写scope、项目绑定及当前角色检查；不新增摘要API，不扩大读取范围。

**回归**：P1-D11-01～08，包括五种现有浏览器写角色、令牌撤销、成员权限撤销、跨项目及行内容不影响授权。原六条契约用例修复前即通过；不能伪造“原失败已修复”。

## D12 · OBS-07-E013 · 回放密文告知、30天与L0/G0

**历史复现步骤**

1. 以项目写角色保存HTTP请求草稿，配置可识别的Header、当前认证和正文测试标记；gRPC Unary作对应验证。
2. 对照页面“仅保存摘要”等旧说明，检查隔离数据库草稿列及授权history返回。
3. 核对草稿列是密文，授权写者能取得解密草稿；区分“加密保存”与“不保存”。
4. 使用可控UTC时钟验证创建后30天前1毫秒、恰好30天及之后；分别准备旧密文、新策略密文、未知/未来时间与坏密文。
5. 执行清理、重复清理及真实JAR重启，检查摘要数量、旧密文字节、未到期密文和到期新密文。

**修复前**：说明与既有加密草稿行为不一致，缺少已批准的到期读取与新策略清理规则。初始14条定向用例2通过、8断言失败、4因尚无策略/清理组件等错误；这些是修复前缺失能力证据，不计入最终通过数。

**落实规则**：A仅保存既有字段白名单；Auth过滤非当前模式隐藏值。UTC创建时间加30天，恰好到期即无草稿；缺失/未来时间禁止回放，坏密文显示不可用。读取和迁入不续期。D11权限始终先判断。

**旧密文保护**：迁移默认`replay_retention_managed=false`，不更新或删除旧密文；L0仅限制读取。迁入旧历史维持非托管。G0只清显式托管且到期的密文列，保留摘要；启动补偿、正常运行最多24小时一次，失败可重试。旧备份/导出文件不清理。隔离数据验证不能冒称已扫描用户全部存量。

**回归**：P1-D12-01～15、P1-U12-01～06；另有HTTP加密失败不落明文、gRPC四种Auth字段、未知时间、清理失败重试、两种数据库升级及真实启动补偿工程检查。已接收的客户端副本、显式导出和备份不在服务端到期物理回收承诺内。

## D03 · OBS-08-E011 · 停用环境的新执行

**历史复现步骤**

1. 创建可执行场景和已定义环境，将场景或运行配置的有效环境指向该环境。
2. 停用环境，通过普通执行、数据驱动、执行预览及手动运行计划提交。
3. 使用合法`run:execute` PAT及有效签名Webhook提交；触发Quartz计划。
4. 检查execution、manifest、outbox、审计及计划连续失败计数。
5. 对照纯配置预览；另在停用前先接受一个任务，停用后验证其原manifest和继续执行的状态。

**修复前**：停用环境仍可从多个入口新建执行；修复前12条中6条失败。

**落实规则**：所有实际提交共用有效环境校验和项目锁；停用时409，无半批任务。Quartz记SKIPPED/ENVIRONMENT_DISABLED，不增加Runner失败数、不自动停用计划。纯配置预览保留；已接受任务继续原快照，重新启用后可接收合法新任务。

**回归**：P1-D03-01～12，包含运行配置覆盖、数据驱动原子拒绝、PAT/Webhook、Quartz、并发停用和已接受快照。未取消旧任务、未补跑跳过批次、未改变共享P2参数环境规则。

## D25 · OBS-16-E003 · 就绪与业务错误一致性

**历史复现步骤**

1. 使用隔离服务端环境，确认MySQL/Redis/S3正常，登录取得有效Cookie；先请求health/readiness/liveness及me。
2. 在仅影响测试客户端的TCP故障边界注入Redis连接拒绝，再注入不回应命令的停滞；不停止共享服务。
3. 带原Cookie重试三种公开探针及me，并验证Redis不可用时的新登录不能假报成功。
4. 计时健康响应，饱和探针后验证liveness仍快速返回且探针线程有上限。
5. 恢复故障边界，再验证readiness和合法会话；普通无认证/无权限及程序缺陷分别保留401/403/500。
6. 桌面模式仅验证本地数据库和文件存储，不补未使用Redis或可选Runner。

**历史事实**：Redis故障时总health503、readiness200、me500。初始受控8条中3条失败；真实Redis验证须单列，不能用夹具替代。

**落实规则**：服务端readiness含数据库/Redis/现有存储，桌面排除未使用Redis。公开探针不依赖Session，隐藏详情；health/readiness最多4线程、不排队、内部4.8秒等待预算满足5秒截止。liveness只查进程状态、独立运行。Redis与存储元数据调用有界；已知依赖不可用返回脱敏503，普通程序错误不改写为503。

**真实故障复验补修**：第一轮真实Redis连接重置发现`RedisSystemException → RedisException → SocketException`分支仍500。补齐仅在Redis异常上下文内的传输故障分类，并新增6条工程回归，保留普通Socket异常和Redis命令编程错误的原错误类别。最终结论必须以补修后的真实HTTP复验为准。

首轮S3工件归档还出现一次502；代码检查发现`ensureBucket`业务初始化复用了新增探针客户端，已恢复为业务原客户端，另加4条测试验证探针故障/关闭不影响业务初始化与延迟建桶。该次502具体底层异常未捕获，不把代码检查结论冒充已确认的单次故障根因；保留首轮结果并复跑完整隔离验收。

**回归**：P1-D25-01～08、既有存储故障/恢复检查、P1RedisHttpFlowTests真实Redis拒绝/停滞/恢复，以及真实桌面JAR正常就绪。这里只验证控制面依赖故障，不代表升级关闭超时已确认修复。
